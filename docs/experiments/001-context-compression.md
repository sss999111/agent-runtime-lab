# 实验 001：上下文压缩策略对比

## 目标

在长文本任务上，对比四种上下文装配策略，看是否能用更少的输入 token 完成同等任务，以及代价是什么。

## 复现命令

模型：doubao-seed-2-1-lite（endpoint id 写入 `.env`，不在仓库）。
任务：`evals/tasks/task_011.json`（从一份约 4800 字的报告中找出三个风险）、`evals/tasks/task_012.json`（判断作者建议优先处理哪个风险）。

```
python bench.py --strategy full      --tasks task_011,task_012 --repeat 3
python bench.py --strategy window    --tasks task_011,task_012 --window 2 --repeat 1
python bench.py --strategy state_card --tasks task_011,task_012 --window 2 --repeat 3
python bench.py --strategy summary   --tasks task_011,task_012 --window 2 --repeat 1
```

`state_card` 的一次 `window=4` 试运行（`bench_state_card_20261115_181702.csv`）未纳入主表，因为窗口大小不同。

## 数据来源

所有数字来自 `logs/` 下的 CSV 明细，每行一次任务执行：

- `bench_full_20261115_181742.csv`（每任务 1 次）+ `bench_full_20261115_182510.csv`（每任务 2 次）= 每任务 3 次
- `bench_window_20261115_181813.csv`（每任务 1 次）
- `bench_state_card_20261115_181837.csv`（每任务 1 次）+ `bench_state_card_20261115_182609.csv`（每任务 2 次）= 每任务 3 次
- `bench_summary_20261115_182412.csv`（每任务 1 次）

每一步的原始轨迹（thought / tool / args / observation / tokens / latency）在同目录的 `*.jsonl` 文件里。

## 结果

| 策略 | 通过 | 平均步数 | 平均输入 tokens | 相对全量 | 平均耗时/任务 |
|---|---|---|---|---|---|
| full 全量 | 6/6 | 5.7 | 15,670 | — | 11.6s |
| window 丢历史（保留 2 步） | 2/2 | 6.5 | 11,902 | -24% | 15.0s |
| state_card 结构化状态卡（保留 2 步） | 6/6 | 5.8 | 10,323 | -34% | 13.7s |
| summary 摘要压缩 | 2/2 | 6.5 | 13,064 | -15% | 167s |

## 结论

1. **结构化状态卡最划算**：输入 token 比全量少 34%，6 次全过，耗时只多 18%。做法是把更早的步骤压成「工具名 + 参数 + 结果前 120 字」的条目，保留最近 2 步的完整内容。
2. **直接丢历史会逼模型重读**：window 省了 24% token，但步数从 5.7 涨到 6.5，说明模型为了找回丢失的信息又去读文件。
3. **摘要压缩是负收益**：只省 15% token，耗时却暴涨到全量的 14 倍。原因是每压一次都要多调一次模型，摘要本身也占上下文，且对小模型来说调用延迟占主导。

## 局限与失败案例

- **方差大**：同一任务 `task_012` 在不同运行里输入 token 从 8,254 到 26,564 都有，步数也在 5 到 8 之间。3 次重复只能说明方向，不能当结论。
- **任务偏短**：两个任务都只有 5-8 步，状态卡还没遇到「长任务累积状态信息丢失」的压力。
- **摘要策略样本少**：只跑了 1 次，但耗时已明显异常，方向可信；若要正式比较需单独评估摘要调用的延迟。
- **未测失败场景**：四个策略都全过，无法判断压缩后哪一种在失败任务上退化更严重。

## 下一步

- 把 `state_card` 在更多长任务上重复 5-10 次，确认 token 节省是否稳定。
- 增加会失败的任务，看压缩是否放大失败。
- 进入记忆模块时，状态卡可以直接复用为「情景记忆」的载体。
