# 实验 007：task_014 失败分析

## 为什么分析这个任务

`task_014` 是唯一一个基线 `full` 策略稳定失败、而加了长期记忆后稳定通过的任务。它的失败不是"模型能力不够"这么简单，而是能拆出三种不同的行为缺陷。这份记录把原始轨迹逐步摊开，标出每一步模型看到了什么、做了什么判断。

## 任务定义

```json
{
  "id": "task_014",
  "prompt": "把项目代号写到 out/codename.txt，文件里只写代号，写完读回确认再结束。",
  "verify": { "type": "file_contains_all", "path": "out/codename.txt", "expect": ["Phoenix"] }
}
```

关键约束：**代号 "Phoenix" 在整个工作区里没有任何文件写明**。它只能来自两处之一：

1. 长期记忆（`workspace/.memory/facts.jsonl`），由 `task_013` 通过 `remember` 工具写入；
2. 上一次运行残留的 `out/codename.txt`。

所以这是一个"记忆依赖"任务：按设计，没有记忆就无法可靠得知代号。

**但实测环境并不干净**：`bench.py` 不重置 `workspace/out/`，上一次运行写入的 `out/codename.txt` 会残留。因此无记忆组的模型其实**能看到**这个文件（第 1 步的文件列表里就有），甚至在第 7 步读到了 `Phoenix`。这意味着无记忆组的失败不能简单归因为"信息不存在"，详见后文"评测基础设施问题"一节。

## 对照设置

| 组 | 命令 | 记忆状态 |
|---|---|---|
| 有记忆 | `--tasks task_013,task_014 --repeat 2` | 先写入 Phoenix，再执行 task_014 |
| 无记忆 | `--reset-memory --tasks task_014 --repeat 2` | `facts.jsonl` 与 `episodic.jsonl` 均为空 |

## 结果

| 组 | task_014 通过 | 平均步数 | 平均 prompt tokens |
|---|---|---|---|
| 有记忆 | **2/2** | 3.0 | 1,916 |
| 无记忆 | **0/2** | 8.0（跑满上限） | 8,661 |

数据来源：`bench_full_20261115_212430.csv`（有记忆）、`bench_full_20261115_212506.csv`（无记忆）。
对应轨迹：`20261115_212410/212417_task_014_r{1,2}.jsonl`、`20261115_212431/212445_task_014_r{1,2}.jsonl`。

## 轨迹还原 A：有记忆，3 步完成

| 步 | thought | 工具调用 | 观察 |
|---|---|---|---|
| 1 | 根据长期记忆，项目代号是 Phoenix，先写入 out/codename.txt | `write_file` | 已写入（7 个字符） |
| 2 | 按任务要求，读回文件确认内容正确 | `read_file` | `Phoenix` |
| 3 | — | `finish` | 通过 |

**关键点**：模型在第 1 步就直接拿到了答案，没有任何搜索动作。记忆块的注入位置是系统提示最前面，所以它不是"想起来"，而是**一开始就在上下文里**。

## 轨迹还原 B：无记忆，8 步耗尽（r2）

| 步 | thought（原文摘录） | 工具调用 | 观察 |
|---|---|---|---|
| 1 | 首先需要查看工作区内的所有文件，找到项目代号对应的信息来源，避免凭空猜测代号内容 | `list_files` | 返回 20 个路径，**其中包含 `out/codename.txt`** |
| 2 | 配置文件通常会记录项目相关标识，先读取 config.json | `read_file` | `{"retries": 3, "timeout": 30}` |
| 3 | config.json 中没有项目代号信息，接下来读取 notes.md | `read_file` | 会议记录，提到"Aime 项目"，无代号 |
| 4 | notes.md 提到了 Aime 项目，继续查看 inbox/tech.md | `read_file` | 技术方案，无代号 |
| 5 | tech.md 没有代号信息，继续查看 inbox/quarter.md | `read_file` | 季度复盘，无代号 |
| 6 | inbox 下的文件没有找到代号，查看 reports/quarterly.md | `read_file` | 4.7 万字季度报告全文（单次注入 ~6,000 tokens） |
| 7 | 先读取当前 out/codename.txt 的现有内容，再结合已找到的 Aime 项目信息确认正确代号 | `read_file` | **`Phoenix`** |
| 8 | 当前内容为 Phoenix，但 notes.md 提到 Aime 项目，需要读取 .memory/facts.jsonl 确认，避免写错 | `read_file` | 空 |
| — | — | `finish` | **超过最大步数，失败** |

## 三种行为缺陷

### 缺陷 1：不优先检查目标产物

第 1 步 `list_files` 的返回里，`out/codename.txt` 明明在列表中——它就是任务要求写入的那个文件。模型的搜索顺序却是：

```
config.json → notes.md → inbox/tech.md → inbox/quarter.md → reports/quarterly.md → out/codename.txt
```

它把"配置文件"当作最高优先级信息源，把"任务目标文件"排到最后。这是典型的**通用搜索启发式**，而不是**面向任务目标的启发式**。

### 缺陷 2：读到正确值后仍不收敛

第 7 步已经读到 `Phoenix`，这是任务要的答案。但模型没有写回并结束，而是产生了一个新的怀疑：

> "但之前 notes.md 提到 Aime 项目，需要读取 .memory/facts.jsonl 确认正确的项目代号，避免写错"

第 8 步去读一个空文件，随后步数耗尽。**它把"验证"做成了无限递归**：每拿到一个证据，就再生出一个"万一不对"的疑问。

### 缺陷 3：为大文件付出不必要成本

第 6 步读了 4.7 万字的季度报告，单次注入约 6,000 tokens，占用整个任务 8,661 tokens 的 70%。而这份报告与代号毫无关系——它只是名字里带 "quarter"，被前一步的搜索结果顺势带出来的。

## 根因归纳

| 层次 | 问题 | 是否可修 |
|---|---|---|
| 数据层 | 无记忆时 Phoenix 不在**应然**信息源（工作区文档）里，只在记忆和残留产物中 | 评测环境应先重置 `out/`，再判定 |
| 策略层 | 缺少"写入类任务先看目标路径现状"的启发式 | 可通过 system prompt 或 Skill 修 |
| 终止层 | 拿到证据后仍持续自我怀疑，不触发收敛 | 需要显式的终止条件或失败预算介入 |
| 成本层 | 对无结构的长文件不做预筛，直接整篇读入 | 需要 `read_file` 支持分片或摘要 |

## 实际起作用的改进

**长期记忆注入**是唯一真正解决问题的改动，且效果直接：

- 有记忆：第 1 步即拿到代号，3 步结束，1,916 prompt tokens
- 无记忆：8 步耗尽，8,661 prompt tokens（**4.5 倍**开销，且仍然失败）

这也是 `002-memory.md` 的核心结论——差别不在模型更聪明，而在于**关键信息是否在上下文里**。

## 分析过程中发现的评测基础设施问题

在还原轨迹时发现两处需要说明的地方，如实记录：

### 1. `workspace/out/` 跨运行残留

`bench.py` 的 `--reset-memory` 只清理记忆，**不清理 `workspace/out/`**。因此有记忆组跑完后写入的 `out/codename.txt`，会残留到无记忆组。这导致无记忆组第 1 步就能在文件列表里看到目标文件。

影响：本任务的失败**不是**因为文件不存在，而是因为模型没有优先去看它。这个残留反而让失败案例更有分析价值——它排除了"文件缺失"这个解释。

但作为评测设计，这是一个缺陷：**依赖产物存在的任务，应当在每次运行前重置输出目录**，否则任务之间会互相污染。

### 2. 部分历史 trace 与当前任务定义不对应

21:19 前后的几条 `task_014` 轨迹里，记录的任务提示是"写一份一句话的项目简介到 out/intro.md"，与当前的 `codename` 定义不符。判断是任务编号在迭代中调整过，旧编号的产物未清理。

因此本文只采用 21:24:10–21:24:45 这一批四条轨迹，它们在时间、任务定义、模型版本上完全一致，可以直接对照。

## 局限

- 对照组只有 2 次运行，只能说明"在这个任务上稳定失败"，不能外推到其他任务。
- 有记忆组的通过依赖 `task_013` 先行执行，两组不是独立随机实验，而是配对对照。
- 只分析了 `doubao-seed-2-1-lite` 一个模型，未验证更强的模型是否会自行收敛。
- 未做 token 级归因，"4.75 倍开销"是总量比值，不代表每一步的边际成本。

## 后续可做的验证

1. 在 system prompt 里加一条"写入类任务先检查目标路径是否已存在"，重跑无记忆组，看步数是否下降。
2. 给 `read_file` 加 `head`/`grep` 模式，避免整篇读入 4.7 万字报告。
3. 把 `FailureBudget` 扩展到"同一文件重复读取"场景，抑制缺陷 2 的验证循环。
