# Agent 编排方案横向调研与选型说明

目标：在动手写运行时之前，先搞清楚「别人已经解决了什么」，避免重复造轮子，也避免误把框架能力当成自研成果。

## 一、对比范围

| 方案 | 定位 | 编排模型 | 状态与记忆 | 扩展方式 | 观测能力 |
|---|---|---|---|---|---|
| **LangGraph**（LangChain） | 低层编排框架 | 显式图：节点 + 边 + 条件分支，可循环 | 图状态（TypedDict）+ checkpointer，支持断点续跑与人工介入 | 自定义节点函数 / 工具 | 可与 LangSmith 打通 |
| **OpenAI Agents SDK** | 轻量多 Agent 框架 | Agent + handoff（交接）+ guardrail（护栏） | session 会话级，跨进程持久化需自定义 | function tools、MCP 服务器 | 内置 tracing |
| **Claude Agent Skills** | 能力封装约定 | 不提供运行时，只定义技能包结构 | 无（由宿主运行时管理） | 目录 + `SKILL.md`，渐进式加载 | 无 |
| **AutoGen / CrewAI** | 多 Agent 协作 | 角色对话 / 任务编排 | 会话内为主 | 工具注册 | 部分支持 |
| **本项目 agent-runtime-lab** | 最小可验证运行时 | 单 Agent ReAct 循环 + 并行工具调用 | 三层记忆（工作 / 情景 / 事实）+ 检查点 | manifest 驱动 Skill + 工具插件目录 | JSONL 逐步轨迹 + CSV 基准 |

## 二、关键结论

1. **上下文压缩没有通用答案**：主流框架提供的是「消息裁剪 / 摘要」的钩子，具体策略与阈值要按任务分布调。所以本项目把四种策略做成可切换开关并跑消融，得到「摘要卡片降 34% token 且成功率不变」「调用模型做摘要耗时涨 14 倍」这类可复用结论。
2. **记忆的难点不在存取，在检索与注入位置**：实验发现把记忆拼进用户消息时模型经常忽略，拼进系统提示后遵守率明显提升；这也是本项目把记忆块前置到系统提示的原因。
3. **Skill 与插件是两层**：Agent Skills 的 `SKILL.md` 解决「怎么用工具」（提示词级），MCP 解决「有哪些工具」（进程级）。本项目两者都做了最小实现：Skill 用清单注入打法，插件用目录注册新工具。
4. **观测先于优化**：没有逐步轨迹（每步工具、参数、观察、token、延迟）就无法判断收益来自哪里，因此本项目所有指标都从 JSONL 轨迹汇总得出。

## 三、为什么选择自研最小实现

| 维度 | 用框架 | 自研（本项目） |
|---|---|---|
| 学习目标 | 会用 API，但说不清内部机制 | 能逐行解释循环、上下文装配、记忆注入 |
| 实验可控性 | 框架内部行为不透明，消融难隔离变量 | 每个模块可单开关，便于对照实验 |
| 成本 | 依赖体积大、版本变动快 | 纯标准库，零依赖，可移植 |
| 风险 | 与真实业务框架脱节 | 生态能力（MCP、可视化）需自己补 |

结论：**以「验证机制」为目的选自研，以「快速交付产品」为目的选框架**。如果后续要做产品化，会优先考虑 LangGraph（图编排 + checkpointer 成熟）或 OpenAI Agents SDK（handoff + 内置 tracing），并把本项目的消融结论迁移过去。
