我从零写了一个 Agent 运行时，用真实实验回答 4 个工程问题

项目地址：github.com/sss999111/agent-runtime-lab

为什么造这个轮子

市面上 Agent 框架很多（LangChain、AutoGen、CrewAI），但用它们做项目有个问题：你说不清自己做了什么。简历上写"基于 LangChain 开发了一个 Agent"，面试官追问"上下文怎么压缩的？记忆怎么设计的？"，你只能答"框架帮我做了"。

所以我用纯 Python 标准库从零写了一个 Agent 运行时 agent-runtime-lab，不套任何框架，每一层都自己实现并跑实验。火山方舟的豆包 API 当模型，19 个可自动判分的任务当评测集。

这篇文章讲四个核心设计取舍，每个都带真实实验数字。

问题一：上下文压缩到什么程度会丢关键约束？

Agent 跑多轮后上下文会膨胀，必须压缩。我实现了四种策略：

  • full：全量保留（基线）
  • window：只留最近 N 步，更早的直接丢
  • state_card：把更早的步骤压成「工具名 + 参数 + 结果前 120 字」的结构化卡片
  • summary：调一次模型把历史压成一段摘要

在两个长文本任务（从 4800 字报告里找风险点）上各跑 3 次：

策略通过平均步数平均输入 tokens相对全量耗时
full 全量6/65.715,670—11.6s
window 丢历史2/26.511,902-24%15.0s
state_card 状态卡6/65.810,323-34%13.7s
summary 摘要压缩2/26.513,064-15%167s

结论：结构化状态卡最划算。 省 34% token，成功率不掉，耗时只多 18%。

两个反直觉的发现：

  1. 直接丢历史会逼模型重读 — window 省了 24% token，但步数从 5.7 涨到 6.5，模型为了找回丢失的信息又去读文件，得不偿失。
  2. 摘要压缩是负收益 — 只省 15% token，耗时却暴涨 14 倍。因为每压一次都要多调一次模型，摘要本身还占上下文，对小模型来说延迟占主导。

问题二：三层记忆在什么任务上真正有用？

我设计了三层记忆：

  • L1 工作记忆：当前对话的步骤 + 状态卡
  • L2 情景轨迹：每个任务结束自动写入 episodic.jsonl
  • L3 长期事实：通过 remember 工具显式写入 facts.jsonl

记忆块拼在系统提示最前面，强制模型遵守。

向量检索：长期事实不是简单取最近 N 条，而是用字符 n-gram + 余弦相似度计算与当前任务的相关度，优先返回最相关的事实。比如查"把项目代号写到文件里"，会优先召回"项目代号是 Phoenix"这条，而不是无关的"数据库超时 30 秒"。

做了个对照实验：先让 Agent 记住"项目代号是 Phoenix"，再让它把代号写到文件里。

组别通过平均步数平均 tokens
有记忆（先记再写）4/42.51,966
无记忆（直接写）0/28.0（跑满）9,488

结论：长期事实能把不可完成的任务变成 3 步完成。 对照组不知道代号，反复列文件、读配置，8 步耗尽仍失败。

但也发现一个问题：格式化类偏好遵守率低。早期测试让模型记住"报告用 markdown 格式"，即使注入到系统提示，lite 模型仍大概率输出纯文本。说明软偏好的遵守依赖模型能力，事实检索类记忆比风格偏好更稳定可靠。

问题三：Skill 自进化能不能让 Agent 越用越强？

我把 Skill 定义为「可复用的打法手册」：每个 skill 是一个目录，里面一个 manifest.json，包含触发词和 playbook（步骤说明）。任务开始时按触发词匹配，命中的 skill 的 playbook 注入系统提示。

更关键的是自进化：Agent 可以调用 learn_skill 工具，把一次成功的任务打法写成新的 skill 落盘，下次同类任务自动参照。

还有一个健康度机制：统计每个 Skill 在任务中的成功率，成功率低于 30% 且样本数 ≥3 的 Skill 会被自动禁用，避免劣质打法长期残留干扰后续任务。

验证下来四个能力都跑通了：

  1. 注入：CSV 求和任务自动匹配 csv_sum skill，playbook 进入系统提示
  2. 自进化：learn_skill 生成的 json_config_handler manifest 正确落盘
  3. 热插拔：手动放一个 manifest，reload() 后立即可见，无需重启
  4. 健康度：连续失败的 Skill 自动从匹配结果中过滤

问题四：Agent 跑一半挂了怎么办？（参考字节 Aime 论文）

我读了字节跳动 Aime 的论文（arxiv 2507.11988），里面有个核心概念叫 Progress Management——维护一个全局状态视图，让 Agent 随时知道"已经做了什么、下一步该做什么"。

我实现了两个机制：

1. 进度跟踪（Progress Tracking）

每一步工具调用后，记录「已完成：XX → 结果」，拼成文本块注入系统提示。这样模型不会重复已经做过的事，也不会在多步任务中迷失方向。

2. 断点续跑（Checkpoint / Resume）

每一步执行后把 turns（对话历史）、步数、token 统计存成 JSON。如果任务中断（API 超时、进程被杀），下次加 --resume 参数就能从断点继续，不用从头跑。

验证：用 --max-steps 1 跑一个 3 步任务 → 失败但留下 checkpoint → 加 --resume 续跑 → 从第 2 步继续并完成。

第1次(1步): ok=False steps=1
有 checkpoint: True
[resume] 从第 2 步继续，已有 1 步历史
第2次(resume): ok=True steps=4
checkpoint 已清除: True

附带产出：零额度回归测试

开发过程中遇到一个现实问题：每次跑 19 任务全量回归都烧免费 API 额度，很快就 429 了。

解法是写了个 MockLLMClient，用预设脚本替代真实模型，接口完全一致。这样：

  • 每次代码改动后跑 bench.py --mock，19 任务 0.4 秒全过，0 tokens
  • 只有做效果实验时才调真实 API
  • 并行调用、失败预算、记忆注入、断点续跑这些链路都能在 Mock 下验证

这本身也是个工程能力的体现——可测试、可复现、省成本。
